## 7.3 AI应用中的技术选型决策树

场景1: 需要在移动端识别图片中的物体

决策:
- 对延迟要求高吗? (需要<100ms, 选端侧推理) (可以接受>1s, 选云端)
- 图片是否包含敏感信息? (是, 必须端侧) (否, 可选云端)
- 设备是否常离线? (是, 端侧优先) (否, 云端更灵活)
- 模型大小/精度要求? (小模型足够, 端侧) (需要超大模型, 云端)

结论: 实时/隐私/离线 -> TFLite在端侧推理; 否则 -> 云端API调用

场景2: 需要构建一个企业内部知识库问答系统

决策:
- 数据是否敏感? (是, 本地部署向量数据库 + 本地LLM或严格限制的云端)
- 预算多少? (有限, 用本地Embedding + 小模型 + 开源向量数据库) (充足, 用商业方案)
- 需要哪些功能? (简单问答 -> 基础RAG; 需要工具调用 -> Agent)
- 技术栈偏好? (Java生态 -> LangChain4j + Spring Boot) (Python -> LangChain + FastAPI)

结论: Java团队 + 数据敏感 -> Spring Boot + LangChain4j + 本地Qdrant + 本地小模型

场景3: 需要优化现有商品推荐系统

决策:
- 现有系统是怎样的? (规则/协同过滤 -> 可以渐进式升级)
- 数据量多大? (百万级用户 -> 深度学习排序)
- 实时性要求? (需要秒级响应 -> 召回层用ANN, 排序层用轻模型)
- 有标注数据吗? (有 -> 监督学习训练排序模型) (少 -> 先从规则和协同过滤起步)

结论: 渐进式升级: 先加多路召回(向量+内容) -> 再加模型排序 -> 最后做实时特征

## 7.4 AI应用开发的完整技术栈图谱

### AI应用层 (你的主要工作区):

前端 (Vue3/TS):
- UI框架: Element Plus / Ant Design Vue / Naive UI
- 状态管理: Pinia
- 流式响应: fetch SSE / EventSource / ReadableStream
- Markdown渲染: marked / markdown-it
- 代码高亮: highlight.js / prism.js
- 图表: ECharts
- 本地推理: TensorFlow.js / ONNX Runtime Web (可选)

后端 (Java 17+ Spring Boot):
- Web框架: Spring Boot 3 / Spring WebFlux (需要更高并发时)
- 推理引擎: ONNX Runtime / Deep Java Library (DJL) / 自定义封装TFLite
- LLM框架: LangChain4j (功能全) / 轻量方案: 直接用OkHttp调用API
- 数据库: PostgreSQL (元数据) + Redis (缓存) + Qdrant (向量)
- 消息队列: RabbitMQ (简单) / Kafka (高吞吐)
- 任务调度: Spring Scheduler (简单) / XXL-Job (分布式)

### AI模型层 (逐步深入, 前期会用就行):

基础模型:
- 图像: ResNet/MobileNet/EfficientNet (已预训练, 直接用)
- 文本: BERT/RoBERTa (中文分类/向量)
- 多模态: CLIP (图像-文本对齐)
- LLM: GPT-3.5/4/ Claude / Llama2 / 国产开源模型

部署工具:
- 模型格式转换: ONNX (通用格式, 跨框架)
- 模型量化: ONNX Quantization / TensorFlow Model Optimization
- 推理加速: vLLM (LLM高吞吐) / TensorRT (Nvidia GPU)

### AI基础设施层 (长期成长方向):

部署与运维:
- 容器化: Docker + Docker Compose (本地/小型部署)
- 容器编排: Kubernetes (生产环境高可用)
- 模型存储: 对象存储 (MinIO / S3)
- 监控: Prometheus + Grafana (通用) + Arize (AI专用)
- 日志: ELK Stack (Elasticsearch + Logstash + Kibana)

## 7.5 关键AI概念与传统开发概念对比

| 传统开发概念 | 对应的AI概念 | 类比解释 |
|-------------|-------------|---------|
| 函数/方法 | 模型推理 | 函数是确定性的:f(x)=y；模型是概率性的:P(y|x) |
| 代码库 | 模型权重文件 | 代码是人写的逻辑；权重是从数据中学到的模式 |
| 单元测试 | 验证集/测试集评估 | 单元测试断言确定值；评估看准确率/召回率等指标 |
| 代码重构 | 模型迭代/重训练 | 重构改代码逻辑；重训练用更多/更好的数据优化模型 |
| 版本控制(Git) | 模型版本管理(DVC/MLflow) | Git管代码；DVC管数据和模型 |
| CI/CD | MLOps | 持续集成/部署；加了模型/数据/训练流程 |
| 性能监控 | 推理性能+模型质量监控 | 监控延迟/吞吐量；还监控准确率/漂移 |
| 数据库索引 | 向量索引(ANN) | B树/哈希索引精确匹配；ANN索引做近似最近邻搜索 |
| 规则引擎 | 轻量级模型 | if-else规则；模型从数据中自动学习模式 |
| A/B测试 | 模型A/B测试 | 测产品功能差异；测不同模型/不同Prompt的效果 |
| 缓存策略 | 推理缓存 | 缓存计算结果；缓存相同输入的推理结果 |
| 限流熔断 | 推理服务限流 | 保护后端不被打垮；保护推理引擎不耗尽GPU |
| 配置文件 | Prompt模板/超参数 | 配置控制行为；Prompt控制LLM行为,超参数控制训练 |

## 7.8 长期学习地图 (入职后持续成长)

第一阶段: AI应用层 (入职后0-6个月)
- 目标: 能独立完成中等复杂度的AI应用开发
- 重点: Prompt工程/RAG优化/Agent设计模式/LLM应用评估方法
- 产出: 1-2个生产级AI应用, 建立团队的AI开发最佳实践

第二阶段: AI工程化 (入职后6-18个月)
- 目标: 能设计和优化AI系统的工程架构
- 重点: 模型服务化/推理性能优化/监控告警/成本优化/MLOps基础
- 产出: 团队的AI开发平台/模型管理系统/自动化部署流水线

第三阶段: 模型层入门 (入职后12-24个月)
- 目标: 理解模型训练过程, 能做简单的微调
- 重点: 数据处理/特征工程/微调方法/模型评估/分布式训练基础
- 产出: 1个用自有数据微调过的模型, 或复现1篇经典论文

第四阶段: 专项深入 (入职后24个月以后)
- 目标: 在某一方向成为专家 (如RAG系统/Agent框架/端侧AI/推理优化)
- 重点: 深入研究, 开源贡献, 技术分享, 推动团队/行业技术进步
- 产出: 开源项目/技术专利/行业分享/技术影响力
