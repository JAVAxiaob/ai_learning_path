## 第一部分：AI基础概念题 (30题)

### 难度: 简单

**1. 什么是机器学习？它和传统编程有什么区别？**
- 传统编程：人类编写规则(代码)，输入数据 → 程序输出结果
- 机器学习：输入数据 + 标注结果 → 算法自动学习出规则(模型)
- 核心区别：机器学习让"规则"从数据中自动学习，而非硬编码

**2. 监督学习 vs 无监督学习 vs 强化学习的区别？**
- 监督学习：有标签数据 (x, y)，学习x到y的映射，如图片分类
- 无监督学习：只有x，学习数据内在结构，如聚类、降维
- 强化学习：通过与环境交互获得奖励，学习最优策略，如AlphaGo

**3. 什么是深度学习？和机器学习的关系？**
- 深度学习是机器学习的子集，使用多层神经网络
- 核心特点：自动特征提取，无需人工设计特征工程
- 你的场景：图像/语音/NLP任务首选深度学习方法

**4. 解释什么是"训练"和"推理"？**
- 训练 (Training)：使用训练数据更新模型参数，计算量大，GPU加速
- 推理 (Inference)：用训练好的模型预测新数据，速度快，可CPU/GPU
- 你的角色：Android/Java端主要做推理，训练由Python/数据科学家完成
- 类比：训练 = 编写/编译代码，推理 = 运行程序

**5. 什么是Epoch、Batch、Iteration？**
- Epoch：全部训练数据完整过一遍
- Batch：一次参数更新使用的数据批次（受显存限制）
- Iteration：一个batch完成一次前向+反向传播 = 1次参数更新
- 例：1000条数据，batch size=100，则1个Epoch=10个Iteration

**6. 什么是过拟合和欠拟合？如何解决？**
- 过拟合：训练集表现好，测试集差（记住了训练数据而非规律）
  - 解决：增加数据、数据增强、正则化(L1/L2/Dropout)、Early Stopping
- 欠拟合：训练集/测试集都差（模型太简单）
  - 解决：增加模型复杂度、减少正则化、训练更久

**7. 常见的评估指标有哪些？**
- 分类任务：准确率(Accuracy)、精确率(Precision)、召回率(Recall)、F1
- 回归任务：MAE、MSE、RMSE
- 排序/推荐：NDCG、MAP
- 你的场景：必须用指标量化模型性能，而非"感觉还可以"

**8. 什么是混淆矩阵？**
- True Positive(TP)：正类预测为正类
- False Positive(FP)：负类预测为正类（误报）
- True Negative(TN)：负类预测为负类
- False Negative(FN)：正类预测为负类（漏报）
- 精确率 = TP/(TP+FP)，召回率 = TP/(TP+FN)

**9. 什么是CNN？它为什么适合图像？**
- CNN = 卷积神经网络
- 核心思想：局部感受野 + 权值共享 + 池化下采样
- 适合图像的原因：局部特征识别（边缘→纹理→形状→物体），参数量远小于全连接网络
- 你的应用：Android端图像分类/物体检测的基础

**10. 什么是Transformer？它的核心思想？**
- Transformer = 基于自注意力机制的序列模型（2017年论文提出）
- 核心组件：Self-Attention、Multi-Head Attention、位置编码
- 优势：并行计算、长距离依赖建模能力强
- 你的场景：LLM(GPT/BERT)的基础，理解原理即可，无需手写实现

### 难度: 中等

**11. 解释梯度下降的工作原理**
- 目标：最小化损失函数 Loss(w)
- 方法：沿梯度反方向更新参数 w = w - lr * 梯度
- 直观理解：像"下山"，每一步朝最陡的方向走
- 常见变体：SGD、Adam、AdamW

**12. 什么是Batch Normalization？为什么有用？**
- BN：在每层输入后做归一化，再加上可学习的缩放/偏移参数
- 作用：加速训练、稳定分布、轻微正则化效果
- 推理注意：推理时使用训练时记录的moving mean/variance（固定值）

**13. 数据增强有哪些常见方法？**
- 图像：随机裁剪、翻转、旋转、颜色抖动、MixUp、CutOut
- 文本：同义词替换、随机插入/删除、Back-translation
- 你的场景：Android端的数据预处理不需要做增强（增强只在训练时）

**14. 模型压缩有哪些方法？分别在什么场景使用？**
- 量化 (Quantization)：float32 → int8/int4，Android端必备
  - 优势：体积↓75%，速度↑2-4x，精度↓1-2%
- 剪枝 (Pruning)：删除不重要的权重/神经元，适合冗余度高的大模型
- 知识蒸馏：大模型(教师)教小模型(学生)，适合边缘部署
- 你的场景：端侧部署优先用动态量化/全量化

**15. 什么是Embedding向量？有什么用？**
- Embedding：将离散对象（词/图像/用户ID）映射为低维稠密向量
- 意义：向量间的距离可以表示语义相似度
- 你的应用：RAG的文档向量化检索、推荐系统用户/物品表示
- 类比：类似数据库索引，但支持"语义搜索"而非精确匹配

**16. MobileNet和ResNet的区别？Android端为什么选MobileNet？**
- MobileNet：使用Depthwise Separable Convolution，参数量少、速度快
- ResNet：残差连接，训练更深的网络，精度高但计算量大
- Android端选型：MobileNet系列优先（速度/体积），精度不够再考虑更大模型

**17. 什么是迁移学习？为什么很实用？**
- 迁移学习：在大数据集上预训练的模型，迁移到小数据集任务
- 方式：特征提取（冻结底层，只训练顶层分类器）和微调(Fine-tuning)
- 你的场景：90%以上的应用场景都基于预训练模型迁移

**18. 为什么大模型会有"幻觉"(Hallucination)问题？**
- 幻觉：LLM输出看起来合理但实际错误的内容
- 原因：基于概率生成文本，不具备"事实知识"验证能力
- 缓解方法：RAG（检索增强生成）、Prompt工程明确"不知道就说不知道"、结果校验

**19. RAG和微调 (Fine-tuning) 的区别？什么时候选哪个？**
- RAG：检索外部文档 + Prompt拼接给LLM，知识来自外部数据源
  - 适合：知识更新频繁、需要引用溯源、不想重训模型
- 微调：用领域数据调整模型参数，知识内化到模型权重
  - 适合：风格/格式学习、特定任务优化、隐私数据不可外泄
- 综合：企业级应用通常 RAG + 少量微调效果最好

**20. Agent的核心组件有哪些？**
- Agent = LLM + 工具调用能力 + 规划能力
- 核心组件：1)工具选择 2)规划(分解任务) 3)记忆(对话历史) 4)反思
- 你的场景：与传统"规则引擎+状态机"类似，但用LLM替代硬编码规则

### 难度: 困难

**21. 解释Self-Attention机制的计算过程**
- 输入序列 X (n个token，每个d维)
- 通过3个矩阵投影得到 Q=X*Wq, K=X*Wk, V=X*Wv
- Attention = softmax(Q*K^T/√d) * V
- 直观理解：每个token"看"其他所有token，根据相关性加权组合
- Multi-Head = h个并行Attention，拼接后再投影

**22. 为什么需要位置编码 (Positional Encoding)？**
- Transformer本身无顺序概念（Attention是位置无关的）
- 需要显式加入位置信息：Sinusoidal编码 / 可学习位置向量
- 你的影响：输入序列长度超过模型max_len时，需要截断/分段处理

**23. LoRA是什么？为什么它是LLM微调的首选？**
- LoRA = Low-Rank Adaptation (低秩适配)
- 思想：不更新原模型参数，新增低秩矩阵A*B训练
- 优势：参数量↓99%（10B模型仅训练10-100M参数）、训练速度快、推理无额外开销
- 你的场景：企业LLM定制化的标准方案

**24. 解释Tokenization的作用和挑战**
- Tokenization：文本到token序列的过程（分词/子词切分）
- 常见方案：BPE (GPT)、WordPiece (BERT)、Unigram
- 挑战：多语言/中文分词质量、OOV词处理、token数影响成本
- 你的影响：API调用前需估算token数，控制调用成本

**25. 什么是数据漂移(Data Drift)？如何检测？**
- 数据漂移：线上输入数据分布与训练数据不一致
- 检测方法：KS检验、卡方检验比较分布、PSI指标、监控预测置信度
- 你的场景：生产环境必须监控，否则模型性能会缓慢下降

**26. 如何设计一个可扩展的推理服务架构？**
- 关键点：1)模型服务容器化（Docker+K8s） 2)多模型版本共存 3)推理缓存 4)异步推理接口 5)自动扩缩容
- 你的背景：与传统微服务架构设计高度相似，知识可直接迁移

**27. 大模型推理有哪些性能优化方法？**
- KV Cache：缓存已生成token的key/value，避免重复计算
- 量化：GPTQ/AWQ/INT8/INT4推理
- 批处理 (Batching)：合并多个请求一起推理（提升吞吐）
- 推理框架：vLLM、TensorRT-LLM
- 你的场景：Java后端推理服务可借鉴批处理+缓存思想

**28. 如何评估一个RAG系统的质量？**
- 检索质量：Recall@K（正确文档是否出现在Top-K）
- 生成质量：回答是否基于检索内容、是否完整回答问题
- 端到端评估：人工评估、LLM-as-judge、RAGAS指标
- 你的场景：必须建立评估集，每次Prompt/模型改动后回归测试

**29. 从工程角度，如何降低LLM的推理成本？**
- 缓存：相同问题/热门查询直接返回缓存结果
- 路由：简单问题用小模型，复杂问题用大模型
- Prompt优化：减少无用token，压缩Context长度
- 蒸馏：用大模型输出监督小模型，线上用小模型
- 量化/推理加速：降低单次推理延迟和成本

**30. AI工程和传统后端工程最大的区别是什么？**
- 传统工程：确定性逻辑，单元测试可覆盖所有路径
- AI工程：概率性输出，评估指标驱动，需要持续监控和迭代
- 核心挑战从"代码正确性"转移到"数据质量+模型性能"
- 你的优势：传统工程方法论（CI/CD、监控、灰度发布）扩展到AI场景
- 差异化竞争力：懂传统工程 + 懂AI工程化的人才稀缺

## 第二部分：AI工程实践题 (25题)

### 难度: 简单

**1. 训练模型的完整流程是怎样的？**
1. 数据收集/标注
2. 数据清洗/划分（训练集/验证集/测试集）
3. 模型选型/初始化
4. 训练循环（前向→计算Loss→反向传播→参数更新）
5. 验证集评估，Early Stopping防止过拟合
6. 测试集最终评估
7. 模型导出（ONNX/TFLite）
8. 部署上线（你的工作重点）

**2. Early Stopping是如何工作的？**
- 监控验证集Loss/Accuracy
- 设定patience（容忍多少epoch无改进）
- 当patience次连续无改进时，停止训练
- 效果：防止过拟合 + 节省训练时间

**3. 为什么要做数据归一化/标准化？**
- 归一化：min-max scaling到[0,1]
- 标准化：(x-mean)/std到均值0方差1
- 目的：不同特征的尺度一致、梯度下降收敛更快、避免大尺度特征主导
- 你的注意：推理端必须用训练时的mean/std做相同预处理

**4. 学习率(Learning Rate)为什么重要？太大会怎样？太小会怎样？**
- 太大：loss震荡甚至发散（步子太大错过最优值）
- 太小：收敛太慢，训练时间过长
- 策略：Warmup + Cosine decay / Step decay

**5. 模型服务化和传统Web服务有什么区别？**
- 模型服务：计算密集型（GPU/CPU），延迟较高
- Web服务：I/O密集型（DB/Redis），延迟较低
- 设计差异：模型服务需考虑批处理、模型版本管理、GPU资源调度

### 难度: 中等

**6. 如何设计一个推理服务的API？需要哪些接口？**
- 核心接口：
  - POST /predict：同步推理
  - POST /predict/async：异步推理
  - GET /health：健康检查
  - GET /model/info：模型元信息
  - POST /model/switch：动态切换模型版本
- 你的参考：与传统微服务REST API设计一致，增加模型相关接口

**7. 如何保证推理服务的高可用性？**
- 多实例部署 + 负载均衡
- 健康检查 + 自动重启
- 模型版本隔离（新版本灰度发布，旧版本保留用于回滚）
- 降级方案：模型服务不可用时返回默认值/简化算法
- 你的优势：与传统微服务高可用设计完全一致

**8. 如何做推理性能的Benchmark？关键指标有哪些？**
- 关键指标：延迟(Latency) P50/P95/P99、吞吐(Throughput) QPS、资源占用
- 方法：固定数据集反复推理、不同batch size/并发数测试
- 你的应用：Android端需实测推理时间(ms) + 内存占用(MB)

**9. 如何实现模型的A/B测试？**
- 方案1：流量分割（按用户ID hash分配到模型A/B）
- 方案2：分层实验（部分用户组用新模型）
- 关键要素：统一实验ID追踪、核心业务指标监控、统计显著性检验

**10. 模型文件管理的最佳实践？**
- 版本管理：每个模型文件带版本号/时间戳
- 元数据记录：训练数据、超参数、评估指标、发布说明
- 存储：对象存储(S3/MinIO)，CDN加速下载
- 加载：懒加载（首次推理时才加载）+ 热切换（不重启服务更新模型）
- Android端：模型放assets或动态下发（应用内更新模型）

**11. 端云协同推理的设计思路？**
- 场景：移动端算力有限但实时性要求高，云端算力强但有网络延迟
- 方案：1)轻模型在端侧做快速初筛 2)低置信度/复杂请求转发云端大模型 3)云端返回更精确结果
- 你的实现：Android先跑TFLite快速给出结果，同时异步请求Java后端ONNX模型
- 优势：兼顾用户体验和精度，保护用户隐私

**12. 如何设计一个向量检索系统用于RAG？**
- 步骤：1)文档切分（200-500词一段） 2)每个chunk通过Embedding模型转为向量 3)向量+原文+元数据存入向量数据库 4)用户查询也转为向量，做Top-K相似检索 5)检索结果拼接进Prompt，传给LLM生成答案
- 关键参数：切分粒度、Top-K数、是否重排序(rerank)

**13. 如何处理长文档输入给LLM（超过Context窗口）？**
- 方案：1)检索增强(RAG)只取相关段落 2)摘要压缩 3)分块处理+Map-Reduce合并 4)使用更大Context的模型
- 成本考虑：Context越长token成本越高，需平衡效果和成本

**14. MLOps和DevOps的关系？**
- MLOps = DevOps for ML
- 新增内容：数据版本管理（DVC）、模型训练流水线自动化、模型注册/版本管理、推理服务监控
- 你的复用：CI/CD、容器化、监控告警等DevOps知识直接可用

**15. 如何设计一个持续监控模型性能的系统？**
- 监控内容：系统指标(QPS/延迟/错误率) + 模型指标(预测置信度分布/数据漂移) + 业务指标(CTR/转化率)
- 告警：超出阈值触发告警
- 你的实现：Micrometer + Prometheus + Grafana，传统监控框架直接扩展

### 难度: 困难

**16. 如何评估一个新模型是否值得替换到线上？**
- 步骤：1)离线评估（测试集对比指标） 2)线上小流量灰度（1-5%流量对比业务指标） 3)成本评估（推理速度/资源占用/费用） 4)风险评估（失败案例分析） 5)回滚方案
- 你的关注："指标提升幅度" vs "升级成本+风险"的权衡

**17. 设计一个高并发推理服务需要考虑哪些点？**
- 计算：批处理(Batching)提升GPU利用率、GPU/MIG分片共享
- 内存：模型权重占显存大、冷/热分层管理、KV Cache优化
- 架构：微服务化（业务逻辑与推理分离）、异步队列、弹性扩缩容

**18. 如何实现模型的热更新（不重启服务切换模型）？**
- 方案：1)双模型加载（简单但双倍内存） 2)动态加载（检测新模型文件，加载后切换） 3)代理路由（API网关路由到不同版本实例）
- 关键：确保切换期间零 downtime、请求一致性

**19. 联邦学习(Federated Learning)适用于什么场景？**
- 思想：数据不出端，在各设备训练，只上传模型参数更新
- 适用：数据敏感/隐私合规场景（医疗、个人数据）
- 你的应用：Android端用户画像/行为预测（无需上传原始用户数据）
- 挑战：通信开销、统计异构性、设备计算能力差异

**20. 从0到1构建一个企业级LLM应用的技术选型？**
- 后端：Spring Boot + LangChain4j（Java生态）
- 模型：企业内部/外部LLM API（GPT-4/文心/私有Llama）
- 向量库：Pinecone（SaaS）或 Milvus（私有化）
- 前端：Vue3 + SSE流式响应
- 你的优势：全部在Java/Vue技术栈内完成

**21. 如何设计Prompt模板管理系统？**
- Prompt工程 = 新的"代码"，需要版本管理
- 功能：模板存储（按业务场景分类）、版本管理（可回滚）、A/B测试、变量注入、日志记录
- 你的实现：与传统配置中心类似，Prompt作为动态配置

**22. 如何优化LLM API的调用成本和延迟？**
- 成本优化：缓存高频Query、选合适的模型版本、精简Prompt、限制max_tokens
- 延迟优化：流式输出(Streaming)边生成边返回、并发请求、本地化小模型处理简单任务

**23. 企业内部部署LLM需要考虑哪些合规问题？**

**24. 如何设计一个Agent系统的工具调用框架？**
